Ctrl+키 입력 문제 조사 보고서

Terminalist 프로젝트 — VSCode 통합 터미널에서 Ctrl+키 조합이 동작하지 않는 문제의 조사 과정과 결론.

조사 기간: 2026-03-22 / 참여: Claude (분석/구현), Codex (리뷰/아키텍처), 사용자 (실행/검증)

1. 문제 설명

Terminalist TUI 앱(Textual 기반)을 VSCode 통합 터미널에서 실행하면, Ctrl+A/B/C 등 모든 Ctrl+키 조합이 동작하지 않음. 일반 문자(a-z), 방향키, Enter, Backspace, Tab 등은 정상 동작.

영향 범위: Ctrl+B(prefix), Ctrl+C(인터럽트), Ctrl+D(EOF), Ctrl+Q(종료) 등 모든 Ctrl 조합.
환경: VSCode 1.112.0, Windows 10, Python 3.14, Textual 8.1.1, xterm.js 기반 통합 터미널.

2. 초기 가설과 실패

Claude 가설 1: VSCode가 키를 가로챈다

VSCode가 Ctrl+B(사이드바 토글), Ctrl+C(복사)를 워크벤치 레벨에서 가로채서 터미널 프로세스에 전달하지 않는다고 판단.

시도: prefix 키를 Ctrl+\로 변경, backtick(`)으로 변경.

결과: 틀렸음. 사용자 지적 — "VSCode 파워셸에서는 Ctrl+B/C가 잘 전달되잖아."

Claude 가설 2: Textual win32 필터 버그

Textual의 EventMonitor.run()에서 dwControlKeyState && wVirtualKeyCode == 0 조건이 ConPTY의 Ctrl+키를 필터링한다고 판단.

// 원본 필터 (win32.py:273-277)
if (key_event.dwControlKeyState
    and key_event.wVirtualKeyCode == 0):
    continue  // ← 이것이 Ctrl+키를 버린다고 생각

// 패치: NUL 체크 추가
if (key_event.dwControlKeyState
    and key_event.wVirtualKeyCode == 0
    and key == "\x00"):  // ← 이 조건 추가
    continue

시도: monkey-patch로 EventMonitor.run 교체.

결과: 패치 적용 확인됐으나 여전히 Ctrl+키 동작 안 함.

실패 원인 1: 최초 버전에서 _debug_log 함수 미정의 → NameError → except Exception: pass가 삼킴 → EventMonitor 스레드 사망.

실패 원인 2: 수정 후에도 동작하지 않음 — 가설 자체가 부분적으로만 맞았음.

Claude 가설 3: SIGINT 핸들러로 Ctrl+C 잡기

VSCode가 Ctrl+C를 SIGINT 시그널로 프로세스에 보내니까, signal.signal(SIGINT, handler)로 잡아서 PTY에 전달하면 된다고 판단.

시도: fakeTerm.py 패턴의 SIGINT 핸들러를 App.__init__에 추가.

결과: Textual이 ENABLE_VIRTUAL_TERMINAL_INPUT을 설정하면 ENABLE_PROCESSED_INPUT이 꺼지므로 Windows가 Ctrl+C를 SIGINT로 변환하지 않음. 시그널 핸들러가 호출되지 않음.

Claude 가설 4: textual 소스 파일 직접 수정

설치된 패키지의 win32.py를 직접 수정하면 확실히 동작할 것이라고 판단.

결과: 여전히 동작 안 함. 사용자로부터 정당한 거부 — "textual을 수정하라고 파일을 준 게 아니라, 원인을 분석하라고 준 것." 수정 롤백.

3. 전환점: Raw Input 테스트

사용자 핵심 질문

"VSCode 터미널 파워셸에서는 Ctrl+B/C가 잘 전달되잖아. Textual-Python 단계에서 캐치를 못하는 거 아니야?"

이 질문이 조사 방향을 바꿈.

Claude test_raw_input.py — Win32 INPUT_RECORD 직접 관찰

Textual을 거치지 않고 ReadConsoleInputW로 직접 읽어 모든 필드를 덤프.

Phase 1 (VT input mode — Textual과 동일 모드):
  [1] vk=0x0011  uChar='\x00'  ctrl=LEFT_CTRL    ← Ctrl 키 단독 (modifier)
  [2] vk=0x0000  uChar='\x01'  ctrl=NONE          ← 제어문자! ctrl 플래그 없음!

Phase 2 (Raw mode):
  [1] vk=0x0011  uChar='\x00'  ctrl=LEFT_CTRL    ← modifier
  [2] vk=0x0041  uChar='\x01'  ctrl=LEFT_CTRL    ← vkCode+ctrlState 모두 살아있음

발견: VT mode에서 Ctrl+A/B/C의 제어문자(\x01/\x02/\x03)는 ReadConsoleInputW에 도착함.

Claude test_stdin_read.py — os.read(stdin) 직접 읽기

bytes=[0x01]  decoded=[^A]    ← Ctrl+A 동작!
bytes=[0x02]  decoded=[^B]    ← Ctrl+B 동작!
bytes=[0x03]  decoded=[^C]    ← Ctrl+C 동작!

핵심 발견: os.read(stdin)으로 Linux 드라이버 방식으로 읽으면 Ctrl+키가 완벽히 도착.

Codex 결정적 분석

Textual의 win32 드라이버는 KEY_EVENT_RECORD에서 uChar.UnicodeChar만 추출하고 vkCode, scanCode, ctrlState를 모두 버립니다.

ConPTY VT mode에서 Ctrl+A는 두 개의 별도 INPUT_RECORD로 도착합니다:

  1. vk=0x0011, uChar='\x00', ctrl=LEFT_CTRL — Ctrl 키 자체 (modifier only)
  2. vk=0x0000, uChar='\x01', ctrl=NONE — 제어 문자 (ctrlState가 0!)

두 번째 이벤트는 ctrlState=NONE이므로 필터를 통과합니다. \x01이 XTermParser에 들어가면 ctrl+a로 매핑됩니다. 이론적으로는 동작해야 합니다.

그런데 실제 Textual 앱에서는 동작하지 않습니다. 이유:

  • Textual이 앱 시작 시 \x1b[>1u (Kitty 키보드 프로토콜)을 활성화
  • VSCode xterm.js는 Kitty를 지원하지 않으므로 무시하지만, ConPTY의 입력 전달 방식에 영향을 줄 수 있음
  • test_raw_input.py는 Textual 없이 순수 콘솔 API만 사용하므로 이 영향을 받지 않음
  • 즉, Textual의 콘솔 초기화가 ConPTY의 키 이벤트 생성 방식을 변경하는 부작용이 있을 가능성

5. VSCode가 가로채는 키 (코드로 해결 불가)

키ReadConsoleInputWos.read(stdin)원인
Ctrl+A✓ 도착✓ 도착—
Ctrl+B✓ 도착✓ 도착—
Ctrl+C✓ 도착✓ 도착—
Ctrl+D✗ 안 옴✗ 안 옴VSCode "Add Selection to Next Find Match"
Ctrl+Q✗ 안 옴✗ 안 옴VSCode가 가로챔

Ctrl+D, Ctrl+Q는 VSCode가 프로세스에 전달하기 전에 워크벤치 액션으로 소비합니다. commandsToSkipShell 설정으로 변경 가능하지만, 사용자 VSCode 설정 변경 없이는 해결 불가.

6. 해결 방향: InputBackend 이중화

Codex 제안 아키텍처

┌─ TerminalistWindowsDriver ─────────────────────┐
│                                                 │
│  ┌─ InputBackend (ABC) ───────────────────┐    │
│  │  start(process_message, exit_event)     │    │
│  │  stop()                                 │    │
│  └─────────────────────────────────────────┘    │
│       │                          │              │
│  Win32RecordBackend      VTStdinBackend         │
│  (ReadConsoleInputW)     (os.read(stdin))       │
│  • 외부 터미널 최적       • VSCode 호환          │
│  • vkCode/ctrlState       • Linux 드라이버와     │
│    풍부한 정보              동일 경로             │
│  • resize 네이티브        • resize 별도 처리     │
│                                                 │
│  환경 감지로 자동 선택:                          │
│  TERM_PROGRAM=vscode → VTStdinBackend           │
│  그 외 → Win32RecordBackend                     │
└─────────────────────────────────────────────────┘

os.read(stdin)으로 Ctrl+A/B/C가 동작하는 것은 확인됨. 이 경로를 Textual의 Windows 드라이버 대안으로 사용하면 VSCode에서 Ctrl+키 문제가 해결됩니다.

8. 핵심 교훈

8.1 진단 순서

  1. Textual 밖에서 먼저 확인 — test_raw_input.py로 Win32 API 레벨에서 데이터가 오는지 확인
  2. Textual 안에서 확인 — test_keys.py로 on_key에 도달하는지 확인
  3. 차이점 분석 — 밖에서는 되고 안에서는 안 되면 Textual 내부 문제

8.2 except Exception: pass는 악마

monkey-patch의 except Exception: pass가 NameError를 삼켜서, EventMonitor 스레드가 죽었는데 아무 로그도 안 남김. 디버깅에 수 시간을 낭비.

8.3 가설 검증 없이 수정하지 말 것

필터 버그라고 확신하고 4번이나 패치를 시도했지만, raw input 테스트 한 번이면 "데이터는 도착한다"를 확인할 수 있었음.

9. 현재 상태 및 다음 단계

확정된 사실:
  • os.read(stdin)으로 Ctrl+A/B/C가 VSCode에서 동작함
  • Ctrl+D/Q는 VSCode가 프로세스 전에 가로채므로 코드로 해결 불가
  • IME(한국어) 활성화 시 Ctrl+키가 한글 자모로 변환됨 (별도 문제)
다음 단계: Codex가 VTStdinBackend + TerminalistWindowsDriver 구현 중.
  • VSCode 감지 시 os.read(stdin) 기반 입력 경로 사용
  • 외부 터미널에서는 기존 ReadConsoleInputW 경로 유지
  • Ctrl+D/Q 등 VSCode가 가로채는 키는 prefix 명령 또는 마우스 메뉴로 대체
