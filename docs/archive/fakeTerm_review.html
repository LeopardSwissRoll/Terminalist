💡
목적: Windows 콘솔의 ENABLE_VIRTUAL_TERMINAL_PROCESSING 플래그를 켜서 ANSI escape code가 실제 터미널 제어로 해석되도록 합니다. 이 플래그가 없으면 \x1b[31m 같은 색상 코드가 문자 그대로 출력됩니다.
25def _enable_vt():
26    if os.name != "nt":
27        return
28    import ctypes
29    k32 = ctypes.windll.kernel32
30    h = k32.GetStdHandle(-11)  # STD_OUTPUT_HANDLE
31    mode = ctypes.c_ulong()
32    k32.GetConsoleMode(h, ctypes.byref(mode))
33    k32.SetConsoleMode(h, mode.value | 0x0004)
✅
Good: guard os.name != "nt"로 비-Windows 환경을 빠르게 스킵. ctypes를 함수 내부에서 import하여 Unix에서 불필요한 로딩 방지.
⚠️
주의: GetConsoleMode 실패 시 (redirected pipe 등) 반환값 체크 없이 진행합니다. 치명적이지는 않지만 방어적 코딩 관점에서 if not k32.GetConsoleMode(...): return 추가를 고려할 수 있습니다.

reader() — PTY Output Reader Thread

L91–115 
91    def reader():
92        nonlocal last_size
93        while not stop.is_set():
94            try:
95                data = proc.read(4096)
96                if data:
97                    sys.stdout.write(data)
98                    sys.stdout.flush()
99                # Resize detection
100               new = _terminal_size()
101               if new != last_size:
102                   last_size = new
103                   try:
104                       proc.setwinsize(*new)
105                   except Exception:
106                       pass
✅
Good: 데몬 스레드(daemon=True)로 생성하여 메인 스레드 종료 시 자동으로 함께 종료.
✅
Good: 읽기 루프 내에서 터미널 리사이즈를 폴링으로 감지. Windows에는 SIGWINCH가 없으므로 이 방식이 합리적입니다.
⚠️
주의: proc.read(4096)이 블로킹일 경우 stop.is_set() 체크가 지연될 수 있습니다. pywinpty의 read는 데이터가 없으면 빈 문자열을 반환하므로 큰 문제는 아니지만, 프로세스 종료 후 루프가 약간 늦게 종료될 수 있습니다.
🔴
Race condition: last_size를 메인 스레드(L71)와 reader 스레드(L92, L102)에서 동시에 접근합니다. Python GIL 덕분에 crash는 나지 않지만, 논리적으로 경합 가능. 실질적으로는 리사이즈가 빈번하지 않아 문제가 될 확률은 매우 낮습니다.

_drain_escape() — Terminal Response Filter

L117–189
💡
이것이 이 파일의 핵심 난이도 구간입니다. CLI 앱(Claude 등)이 터미널에 "너 뭐야?" 질의를 보내면, 호스트 터미널(VSCode xterm.js)이 stdin으로 응답합니다. 이 응답이 PTY에 전달되면 자식 프로세스가 혼란에 빠지므로, 반드시 걸러내야 합니다.
Sequence TypePatternExampleHandler
CSI (Control Sequence) ESC [ ... <final> \x1b[?61;6;7c (DA Response) 끝 문자가 c, y, n이면 discard
DCS (Device Control) ESC P ... ESC \ \x1bP>|xterm.js\x1b\\ ST 종결자까지 읽고 discard (0.5s timeout)
OSC (Operating System) ESC ] ... BEL|ST \x1b]0;title\x07 BEL 또는 ST까지 읽고 discard (0.5s timeout)
Unknown ESC + char \x1b + a (Alt+A) 사용자 입력으로 판단 → PTY에 forward
✅
Good: 3가지 주요 escape sequence 타입(CSI, DCS, OSC)을 모두 처리. DCS/OSC에는 0.5초 타임아웃을 두어 불완전한 시퀀스에 의한 행(hang) 방지.
✅
Good: 반환값 설계가 명확 — None = 터미널 응답(discard), str = 사용자 입력(forward). 호출부에서 분기가 깔끔합니다.
⚠️
Edge case: CSI 필터(L150)에서 n으로 끝나는 시퀀스를 모두 discard하는데, 사용자가 Alt+[ 후 n을 누르면 의도치 않게 삼켜질 수 있습니다. 실제로는 거의 발생하지 않는 케이스입니다.
⚠️
Timing: CSI 파서(L141)는 msvcrt.kbhit()가 false면 즉시 종료하여 시퀀스를 일부만 읽을 수 있습니다. DCS/OSC와 달리 timeout 루프가 없는데, 이는 CSI 응답이 보통 한 번에 도착하기 때문에 실용적으로는 문제없습니다.

Overall Assessment

● Strengths

  • 250줄로 완전한 PTY passthrough 구현 — 군더더기 없는 minimal 설계
  • Windows PTY의 까다로운 점(VT처리, 특수키, escape 필터링)을 모두 처리
  • 터미널 응답 필터링이 3개 escape 유형(CSI, DCS, OSC)을 정확히 구분
  • 더블 Ctrl+C 탈출 UX가 직관적이고 안전
  • 리소스 정리(finally, daemon thread)가 빈틈없음
  • lazy import로 cross-platform import 안정성 확보
  • 주석이 풍부하고 각 섹션의 역할이 명확

● Improvements

  • F1-F12 키 매핑 누락 — 일부 CLI에서 필요
  • 2초 initial drain이 사용자 입력도 무시
  • CSI 파서에 timeout이 없어 느린 터미널 응답 시 부분 파싱 가능
  • GetConsoleMode 실패 시 에러 체크 없음
  • last_size의 스레드 간 경합 (실질적 문제는 낮음)
  • Windows 전용 — Unix에서는 동작하지 않음 (의도된 제한)
